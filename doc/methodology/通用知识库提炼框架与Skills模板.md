# 通用知识库提炼框架与Skills模板

> 基于《史记》知识库项目抽象出的通用方法，适用于古籍、制度文献、政策文本、案例库、行业规范等可分章分篇的大型语料。

---

## 一、从《史记》项目抽出的结构骨架

《史记》项目表面上是一个古籍标注与展示仓库，实际内部已经形成了一个完整的知识提炼系统。它的核心不是某个脚本，而是四层递进结构与若干横切能力。

### 1.1 四层主结构

| 层级 | 本项目对应目录 | 在项目中的职责 | 通用抽象 | 可迁移性 |
|------|----------------|----------------|----------|----------|
| 源文本层 | `archive/`, `docs/original_text/` | 保存原始文本、定本、校勘结果 | Source of Truth | 高 |
| 结构文本层 | `chapter_md/`, `tables/` | 章节切分、段落编号、区块语义、注释层 | Structured Corpus | 高 |
| 知识图谱层 | `kg/`, `ontology/` | 实体、事件、关系、本体、推理、SKU | Knowledge Layer | 高 |
| 应用交付层 | `docs/`, `app/` | 阅读器、索引页、地铁图、游戏、静态发布 | Delivery Layer | 高 |

### 1.2 五个横切能力

| 能力 | 本项目体现 | 通用价值 |
|------|------------|----------|
| Schema 设计 | 18类实体、事件类型、SKU类型 | 决定知识库长期可维护性 |
| 渲染与发布 | `render_shiji_html.py`, `generate_all_chapters.py` | 让结构化知识可消费 |
| 质量闭环 | lint、validate、反思审查 | 降低 LLM 误标和结构漂移 |
| 方法论沉淀 | `skills/` | 将一次性项目变成可复制工艺 |
| 产物分层 | 文本、索引、图谱、SKU、应用分开存放 | 避免数据和展示耦合 |

### 1.3 《史记》项目最值得复用的不是内容，而是组织方式

可以迁移的核心设计：

- 先定本，再结构化，再抽知识，再做应用。
- 用轻量可逆标记表达语义，避免直接把 HTML 写进源文本。
- 将“实体、事件、关系、本体、推理、SKU”作为独立层次，而不是一次性抽成 JSON 就结束。
- 每一层都要有验证脚本或审查回路。
- 方法论文档和数据产物同等重要，因为后者会过时，前者决定能否重建。

《史记》特有、迁移时应替换的部分：

- 三家注处理。
- 十表专用结构。
- 先秦到西汉的纪年体系。
- 古代官职、姓氏、谥号等特定消歧规则。
- 面向古籍阅读器和历史游戏的终端形态。

## 二、通用知识库提炼框架

### 2.1 总体管线

```text
原始语料
    ↓
G01 定本与校勘
    ↓
G02 结构切分与锚点编号
    ↓
G03 实体/术语标注
    ↓
G04 事实/事件抽取
    ↓
G05 关系网络构建
    ↓
G06 本体/词表构建
    ↓
G07 推理、审查与修正
    ↓
G08 SKU/知识单元封装
    ↓
G09 应用构造与发布
```

这个框架适合处理“可切分、可引用、可核验”的语料。它不要求语料一定是古籍，但要求文本中存在稳定的知识对象、事件或规则。

### 2.2 九阶段抽象

| 阶段 | 目标 | 典型输入 | 典型输出 | 核心问题 |
|------|------|----------|----------|----------|
| G01 定本与校勘 | 确立可信文本基线 | PDF、EPUB、扫描件、网页正文 | 定本 `.txt`/`.md` | 基础文本是否可靠 |
| G02 结构切分与锚点编号 | 把连续文本切成可引用单元 | 定本 | 按篇、节、段、句编号的结构文本 | 后续知识能否精准回指 |
| G03 实体/术语标注 | 找出“文本中是什么” | 结构文本 | 标注文本、实体索引、别名表 | 核心对象有哪些 |
| G04 事实/事件抽取 | 找出“发生了什么” | 标注文本 | 事实三元组、事件记录 | 文本中的行为和状态变化是什么 |
| G05 关系网络构建 | 找出“彼此如何关联” | 实体、事件、事实 | 关系图、因果链、引用链 | 局部知识如何组成网络 |
| G06 本体/词表构建 | 找出“如何分类与约束” | 实体与关系网络 | taxonomy、RDF/OWL、词表 | 这些知识遵循什么分类体系 |
| G07 推理与审查 | 找出“哪里不一致、哪里可推断” | 图谱、本体、时间信息 | 修正规则、推理结果、审查报告 | 怎样把原始抽取变成可用知识 |
| G08 SKU 封装 | 把知识变成可分发单元 | 事实、关系、规则、主题材料 | factual/procedural/relational SKU | 如何让知识可复用、可组合 |
| G09 应用与发布 | 让知识被用户消费 | SKU 与图谱 | 网站、问答、检索、可视化、API | 如何把知识转成体验 |

### 2.3 每个阶段都要回答的五个问题

1. 这一层的最小工作单元是什么。
2. 这一层的输入是原文、结构单元还是上游知识对象。
3. 这一层的输出是否能被下游直接消费。
4. 这一层的验证标准是什么。
5. 这一层的错误是“可接受偏差”还是“必须阻断”。

### 2.4 通用最小数据单元

建议任何知识库项目至少定义以下六类对象：

| 对象 | 说明 | 《史记》项目对应 |
|------|------|------------------|
| Document | 文档或章节级单元 | `chapter_md/*.tagged.md` |
| Anchor | 可定位的段、句、条目编号 | Purple Numbers 段落编号 |
| Entity | 人、地、机构、术语、制度等对象 | 18类实体 |
| Event/Fact | 行为、状态、规则、事实三元组 | `kg/events/`, `kg/relations/`, `kg/facts/` |
| Ontology Term | 分类概念、标签、约束规则 | `kg/rdf/`, `vocabularies/` |
| SKU | 面向消费的知识单元 | `ontology/skus/` |

如果缺少 Anchor，知识无法回到原文；如果缺少 SKU，知识难以被产品层复用。

### 2.5 通用目录模板

```text
kb-project/
├── source/                 # 原始语料、底本、扫描件
├── corpus/                 # 定本、切分后的文本
├── schema/                 # 实体类型、事件类型、校验规则、本体定义
├── kg/
│   ├── entities/           # 实体索引、别名、消歧
│   ├── events/             # 事件或事实索引
│   ├── relations/          # 关系网络、三元组、因果链
│   ├── chronology/         # 时间轴、版本轴、时序映射
│   ├── ontology/           # taxonomy / RDF / OWL / glossary
│   └── reports/            # 质量报告、审查报告、统计结果
├── ontology/skus/          # 面向应用的知识单元
├── skills/                 # 方法论文档与操作规范
├── scripts/                # lint、validate、build、publish 工具
├── docs/                   # 发布产物
└── app/                    # 应用层（检索、问答、可视化等）
```

### 2.6 三条通用设计原则

#### 原则一：内容与样式分离

源文本里的结构标记应尽量轻量、可逆、可 diff。渲染、配色、链接、跳转都放到程序层完成。

#### 原则二：LLM 负责语义理解，规则负责约束和收敛

适合交给 LLM 的工作：

- 实体识别与边界判断。
- 事件粒度判断。
- 段间语义关系归纳。
- 本体初次分类。

适合交给规则和脚本的工作：

- 格式校验。
- ID 连续性检查。
- 别名归并。
- 时间映射。
- 去重、冲突检测、覆盖率统计。

#### 原则三：每一层都要有“反思回路”

建议任何项目都至少保留三种审查：

- 格式审查：是否破坏了结构和约定。
- 语义审查：分类、边界、归属是否合理。
- 交叉审查：与权威表、已有索引、上下游数据是否冲突。

## 三、通用 Skills 套件

《史记》项目的 `skills/` 实际上已经接近一套领域知识工程 SOP。把它抽象后，可以得到一组通用 Skills。

### 3.1 推荐的核心 Skills

| 通用 Skill | 目标 | 主要输入 | 主要输出 | 对应《史记》工序 |
|------------|------|----------|----------|------------------|
| G00 管线总览 | 定义全局流程、边界和依赖 | 项目目标、语料类型 | 总控文档、阶段图 | `SKILL_00_管线总览.md` |
| G01 定本与校勘 | 获得可信文本基线 | 原始语料 | 定本、校勘表 | `SKILL_01_古籍校勘.md` |
| G02 结构切分与编号 | 建立可引用锚点 | 定本 | 章节/段落/句子结构 | `SKILL_02*` |
| G03 实体与术语标注 | 建立对象层 | 结构文本 | 标注文本、实体索引 | `SKILL_03a.md` |
| G04 消歧与规范化 | 统一对象名 | 实体索引、上下文 | 规范名、别名表、消歧映射 | `SKILL_03b.md` |
| G05 事实/事件抽取 | 建立行为与状态层 | 标注文本 | 事件索引、事实三元组 | `SKILL_04a.md`, `SKILL_05c.md` |
| G06 关系发现 | 建立网络层 | 实体、事件、事实 | 关系图、因果链、引用链 | `SKILL_05a.md`, `SKILL_05b.md` |
| G07 本体与词表构建 | 建立分类与约束层 | 实体和关系 | taxonomy、词表、RDF | `SKILL_06a.md` |
| G08 时间/规则推理 | 做审查、补全与冲突检测 | 图谱、本体、时序 | 推理结果、修正建议 | `SKILL_04c.md`, `SKILL_07*.md` |
| G09 反思审查 | 把误差收敛成稳定资产 | 各层中间产物 | 审查提示、修正记录、报告 | `SKILL_03c.md`, `SKILL_04d.md` |
| G10 SKU 封装 | 把知识变成可分发单元 | 事实、关系、规则 | factual/procedural/relational SKU | `SKILL_08_SKU构造.md` |
| G11 渲染与发布 | 生成用户可访问产物 | 标注文本、SKU | HTML、索引页、静态站点 | `SKILL_03d.md`, `SKILL_09a.md` |
| G12 应用构造 | 面向场景消费知识 | SKU、图谱 | 搜索、问答、地图、时间线、游戏 | `SKILL_09.md`, `SKILL_09b.md` |

### 3.2 可选扩展 Skills

这些不是所有项目都需要，但一旦规模变大就会非常有价值：

- G13 表格/清单结构语义：针对年表、清单、指标表等非叙事文本。
- G14 注释层处理：针对脚注、批注、审校意见、版本异文。
- G15 多源对齐：同一事件或概念在多份文献中的对齐。
- G16 统计分析：词频、密度、覆盖率、异常值发现。
- G17 证据追踪：每个事实保留原文证据和置信度。
- G18 变更治理：处理 schema 版本升级和批量迁移。

### 3.3 单个 Skill 的标准模板

建议以后新增 Skill 时统一使用下面的结构。这个模板基本就是《史记》项目现有高质量 Skill 的共性。

```markdown
# SKILL: {名称}

> 这一工序解决什么问题，位于整条管线的什么位置。

## 1. 任务定义
- 目标是什么
- 不解决什么

## 2. 前置条件
- 依赖哪些上游产物
- 输入必须满足什么格式

## 3. 输入
- 文件
- 数据结构
- 参考资料 / ground truth

## 4. 输出
- 产物文件
- 数据字段
- 供下游消费的接口

## 5. 核心规则与判断标准
- 分类标准
- 边界条件
- 例外情况

## 6. 执行步骤
1. 预处理
2. 主提取
3. 后处理
4. 汇总与索引

## 7. 验证
- lint 规则
- 统计检查
- 抽样审查
- 交叉验证

## 8. 常见失败模式
- 漏标
- 误标
- 过度切分
- 锚点漂移
- 规范名不一致

## 9. 与上下游的依赖关系
- 上游依赖
- 下游消费者
```

### 3.4 建议优先沉淀的五份通用 Skill

如果只想最小投入做出可复用方法，优先写这五份：

1. `G00_管线总览`：定义全局数据流、目录结构、阶段边界。
2. `G02_结构切分与编号`：保证所有知识可回指原文。
3. `G03_实体与术语标注`：保证对象层稳定。
4. `G05_事实事件抽取`：建立真正可计算的知识层。
5. `G09_反思审查`：保证系统会收敛，而不是越做越脏。

这五份足够支撑一个知识库 MVP；剩余 Skills 可以随着规模逐步展开。

## 四、把《史记》方法迁移到其他知识库时，真正要替换的只有六个面

| 面向 | 需要替换的内容 | 例子 |
|------|----------------|------|
| 语料单元 | 章、节、条、案例、法条、问答对 | 古籍章节、司法判例、政策条文 |
| 实体类型 | 人地事物、机构、术语、产品、条款 | 古籍 18 类，法规可换成主体/义务/处罚 |
| 事件类型 | 战争、继位、政策、违规、操作、告警 | 历史事件可换成业务流程事件 |
| Ground Truth | 年表、权威索引、标准词表、外部数据库 | 历史年表、术语库、组织架构表 |
| 本体结构 | 分类树、关系约束、字段定义 | 官职体系、法条体系、产品目录 |
| 终端形态 | 阅读器、检索、问答、流程图、监控看板 | 地铁图可以换成依赖图、时序图 |

换言之，通用框架是稳定的，变化的是领域 schema 与权威参照。

## 五、给未来项目的落地建议

### 5.1 先做最小闭环，不要一开始追求全栈豪华版

建议先完成下面这条最小闭环：

```text
定本
→ 结构切分
→ 实体标注
→ 事实/事件抽取
→ SKU 封装
→ 简单检索/阅读界面
```

只要这个闭环能跑通，后面的关系、本体、推理、游戏化、复杂可视化都可以逐步叠加。

### 5.2 不要让知识库沦为“只有 JSON、没有方法”的一次性项目

必须同步维护三类资产：

- 数据资产：文本、图谱、SKU。
- 工具资产：build、lint、validate、publish 脚本。
- 方法资产：skills、规范、失败案例、修正原则。

三者缺一，项目都难以长期扩张。

### 5.3 推荐的成熟度分级

| 等级 | 特征 |
|------|------|
| L1 文本结构化 | 有定本、切分、锚点编号 |
| L2 对象层 | 有实体/术语标注和索引 |
| L3 知识层 | 有事件、事实、关系 |
| L4 语义层 | 有本体、规则、推理 |
| L5 产品层 | 有可消费应用与可复用 SKU |

《史记》项目已经接近 L5，因此非常适合作为通用框架母体。

---

## 六、结论

《史记》知识库项目最有价值的部分，不是“把《史记》做成了网站”，而是已经沉淀出一套可以迁移的知识工程生产线：

- 以定本和结构锚点保证可回溯。
- 以实体、事件、关系、本体形成知识层。
- 以审查和反思形成质量闭环。
- 以 SKU 和应用把知识转成可分发、可消费的产物。
- 以 Skills 把经验从“人脑里的做法”变成“可复制的工艺”。

如果后续要把这套方法推广到别的项目，最佳做法不是重写整套系统，而是保留这条九阶段框架，只替换领域 schema、权威参照和交付形态。
