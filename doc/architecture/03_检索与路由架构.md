# 检索与路由架构

> 本文定义系统运行时如何从静态知识资产中检索证据，并基于问题类型选择最合适的检索路径。

---

## 一、设计原则

1. 先检索证据，再生成答案。
2. 先走最便宜的路径，再触发更重的路径。
3. 问题复杂度上升时，优先叠加新模块，而不是替换底座。

---

## 二、三类框架的职责边界

### LlamaIndex

职责：

- 数据接入
- 索引构建
- 基础检索
- 检索器封装

适用层：

- 运行时知识引擎底座

### GraphRAG

职责：

- 图谱增强检索
- 社区聚类与社区摘要
- 全局问题与跨文档问题强化

适用层：

- 高阶全局检索策略

### LangGraph

职责：

- 多步骤流程编排
- 回退、重试、人工复核
- 多检索通道结果汇总

适用层：

- 运行时控制平面

结论：

- LlamaIndex 解决“怎么查”
- GraphRAG 解决“图谱问题怎么查得更好”
- LangGraph 解决“整个流程怎么跑得稳”

---

## 三、系统中的检索资产

建议把运行时可用索引分成五类：

1. **Anchor / Passage Index**
   - 原文片段与锚点回读
2. **Entity Index**
   - 规范名、别名、章节消歧、引用分布
3. **Event / Relation Index**
   - 事件节点、关系边、因果链
4. **Ontology / SKU Index**
   - factual、procedural、relational 打包知识单元
5. **Chronology / Structured Filters**
   - 时间、章节、人物、类型过滤条件

---

## 四、Optimized Tool Selection

### 问题分类

| 问题类型 | 主路径 | 备路径 |
|----------|--------|--------|
| 单事实问答 | Entity / Passage | Event |
| 人物关系追踪 | Relation | Passage |
| 事件因果链 | Event + Relation | Passage |
| 专题综述 | Ontology / Graph Community | Passage |
| 时间筛选问题 | Chronology | Event / Passage |
| 规则或方法问题 | Procedural SKU | Passage |

### 路由规则

1. 如果问题带明确实体名，先查实体规范名。
2. 如果问题带明确章节或时间约束，先用结构化过滤降噪。
3. 如果问题是“如何做”“有什么方法”，优先查 procedural SKU。
4. 如果问题是“总体如何”“有哪些模式”，优先查 ontology 或社区摘要。
5. 如果高层答案缺少证据，必须回跳到原文片段。

---

## 五、ontology 在检索中的作用

ontology 不应替代原文和图谱，而应承担两个角色：

1. **高层知识入口**
   - 让系统快速进入一个主题域
2. **打包证据容器**
   - 让系统知道该去哪些实体、事件、关系和章节继续取证

因此，ontology 更适合作为：

- 首轮召回的主题入口
- 复杂问题的结构化中间层

而不是：

- 唯一事实来源
- 无需回证据的终局答案库

---

## 六、阶段路线

### 阶段 1

先做：

- Anchor / Entity / Event / Ontology 的统一查询接口

### 阶段 2

增强：

- GraphRAG 社区摘要
- 主题级全局检索

### 阶段 3

编排：

- LangGraph 工作流
- 多路召回
- 冲突检测与回退

这一路线保证系统始终建立在可追溯证据之上，而不是把复杂度一开始就堆满。
