# 实体抽取与知识装配架构

> 本文回答三个问题：实体抽取层和 `ontology/` 的关系是什么；现有框架是否已经覆盖 ontology 的工作内容；后续应补的是哪一段子管线。

---

## 一、核心判断

### 结论一

**不需要新建一套实体抽取框架。**

现有实体层已经具备完整的主干能力：

- 实体识别
- 实体分类
- 别名归并
- 章节级消歧
- 规范名统一
- 锚点回指

这些能力已经在 [SKILL_03a_实体标注](../../skills/SKILL_03a_实体标注.md) 中被系统定义，也通过 [disambiguate_names.py](../../kg/entities/scripts/disambiguate_names.py) 等脚本落地。

### 结论二

**需要新增一条 ontology 装配子管线。**

原因是 `ontology/` 当前主要体现为结果资产，而不是完整纳入主干的装配流程。

---

## 二、现有实体层已覆盖的内容

### 1. 标注层

现有系统通过 `〖TYPE〗` 轻量标记体系完成实体标注，已覆盖 18 类对象，包括：

- 人名、地名、官职、身份、时间
- 氏族、邦国、制度、族群
- 器物、天文、神话、生物
- 典籍、礼仪、刑法、思想、数量

这意味着实体层已经不是“是否抽到实体”的问题，而是**抽到之后如何稳定治理**的问题。

### 2. 规范化层

实体层已具备：

- canonical name
- alias 映射
- 章节级消歧
- 内联消歧语法

这部分能力对 ontology 非常关键，因为 SKU、关系三元组和运行时检索都不能直接依赖原文表层名称。

### 3. 索引层

现有实体层已经输出：

- `entity_index.json`
- `entity_aliases.json`
- `disambiguation_map.json`

这些文件构成了 ontology 的实体输入底座。

---

## 三、ontology 目前如何复用实体层

最直接的证据是 [augment_sku_entities.py](../../kg/entities/scripts/augment_sku_entities.py)。

它的工作机制是：

1. 读取 `entity_index.json` 与别名数据。
2. 扫描 `ontology/skus/factual/*` 下的内容。
3. 为每个 factual SKU 生成 `entities.json`。
4. 回写 `skus_index.json` 中的 `entity_count` 与 `top_entities`。

这说明：

**ontology 当前并没有重新做一套实体抽取，而是在消费现有实体层的结果。**

因此两者关系应定义为：

- 实体层 = 基础知识抽取层
- ontology = 知识装配与打包层

---

## 四、现有框架对 ontology 的覆盖情况

| ontology 工作内容 | 现有框架覆盖度 | 说明 |
|------------------|----------------|------|
| factual SKU 的实体增强 | 高 | 已由实体索引回填完成 |
| factual SKU 的候选生成 | 中 | 有结果，但主生成链主要来自外部工具 |
| procedural SKU 提炼 | 中低 | 有结果目录，但现有九阶段缺少正式装配定义 |
| relational 装配 | 中 | 关系构建与本体构建已覆盖上游，但 label tree / glossary / relationships 打包未正式入主干 |
| bucketing / dedup / confidence | 低 | 有结果资产，但未纳入主流程设计 |

关键判断：

**现有框架已经覆盖 ontology 的上游知识生产，但未完整覆盖 ontology 的装配、治理和发布链路。**

---

## 五、应新增的 ontology 装配子管线

建议把当前第 08 阶段从“抽象的 SKU构造”细化为五个模块：

### O1 SKU 候选生成

输入：

- entity index
- event index
- relation triples
- ontology terms

输出：

- SKU candidate list
- SKU 粒度建议
- source chunk 列表

### O2 Factual 装配

输入：

- 事实三元组
- 事件索引
- 实体锚点

输出：

- `header.md`
- `content.md` 或 `content.json`
- `entities.json`

### O3 Procedural 提炼

输入：

- 多个事实案例
- 事件模式
- 关系网络

输出：

- `SKILL.md`
- 适用条件
- 步骤化方法
- 风险与边界

### O4 Relational 打包

输入：

- taxonomy
- glossary candidates
- typed relationships

输出：

- `label_tree.json`
- `glossary.json`
- `relationships.json`

### O5 治理与后处理

输入：

- 全量 SKU 结果

输出：

- `skus_index.json`
- `bucketing_result.json`
- `dedup_report.json`
- confidence / contradiction / merge reports

## 六、架构原则

### 原则一：实体层是 ontology 的底座，不是替代品

ontology 不能跳过实体层直接从原文自由生成，否则会失去规范名、消歧和可追溯性。

### 原则二：ontology 层负责“装配”，不负责“篡改事实”

ontology 可以重组、聚类、摘要和分类，但不能脱离锚点重新发明事实。

### 原则三：procedural 与 relational 不能只靠实体匹配生成

factual 可以大量继承实体层结果，但 procedural 和 relational 需要额外的抽象、聚类和规则治理。

## 七、对现有设计文档的补充要求

后续在 `doc/spec/` 或 `skills/` 中，应继续补齐以下内容：

1. SKU 粒度标准
2. SKU 证据字段标准
3. procedural 提炼规则
4. relational 谓词白名单与语义约束
5. confidence 评分方法

这五项补齐后，现有九阶段框架就能正式覆盖 ontology 的工作内容，而不需要另造一套实体体系。
